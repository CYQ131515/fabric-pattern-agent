# 四方连续生成器

把一张花型图变成可以无缝平铺（四方连续）的印花单元。

**分工原则：算法搭骨架，大模型补最后一块。**

能算准的事绝不交给模型 —— 位移、遮罩、强制还原、边界对齐全部由 NumPy + Pillow 完成，
确定性、零成本、可复现。模型只负责算法算不了的那一件事：**判断中央十字带该怎么接续**。

---

## 一、为什么这样设计

一张图不能平铺，根因是"最右一列和最左一列对不上、最下一行和最上一行对不上"。

所以第一步不是修，而是**把问题挪个位置**：整张图平移半幅，
四条问题边就集中到画面正中央变成一个十字。此时画面外围全是原图内容，天然连续。

然后：

1. 算法用一块**中央十字带 mask** 框出"只许改这里"的范围；
2. `deepseek-v4.1-flash` 看图，判断图案类型、中央十字坏在哪、该怎么接续；
3. `gpt-image-2.5-flare` 按诊断结果做**局部重绘**（真传 mask，不是靠嘴说）；
4. `compose` 把 mask 之外的像素**强制还原成原图** —— 不管模型在别处画了什么，一律丢掉；
5. `wrap_align` 做像素级边界对齐，兜住模型最后一点误差。

**第 4 步是保真的根本保障，不是可选项。** 实测：生成类模型会顺手把整张图重画一遍
（非接缝区改动 50+ 灰阶、结构相关掉到 0.19），靠"请保持其余不变"这种话是拦不住的。
只有架构上强制还原才拦得住。

## 二、安装与使用

```bash
pip install -r requirements.txt
# 或者直接双击「安装.command」——它会建好 .venv 再装（主程序就是找这个 .venv）

# 纯算法：不需要 key，零成本，结果确定性
python run.py -i 花型.jpg -o out/

# 全流程：诊断 + 补缝（默认一个网关两用，一把 key 全包）
python run.py -i 花型.jpg -o out/ --key sk-xxx

# key 也可以走环境变量
export APIMART_API_KEY=sk-xxx
python run.py -i 花型.jpg -o out/

# 想把诊断拆到别的网关（比如更便宜的那家），再补一组 base + key：
python run.py -i 花型.jpg -o out/ --key sk-出图网关的key \
    --analyze-base https://api.deepseek.com/v1 --analyze-key sk-诊断网关的key
```

只给 `--key` 就是单网关模式（诊断也走那家）—— **这是默认形态**。

常用参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--candidates N` | 1 | 出图跑 N 个候选自动挑最优（模型不可复现，建议 2~3） |
| `--mask-band` | 0.07 | 中央十字带宽度占比。越大给模型自由度越高，越小保真越好 |
| `--analyze-key` | 空 | 诊断线的 key。留空 = 诊断沿用出图那套（单网关） |
| `--base-url` / `--analyze-base` | 见第四节 | 出图 / 诊断的网关地址 |
| `--no-analyze` | 关 | 跳过诊断，用通用指令直接出图 |
| `--no-model` | 关 | 只跑纯算法 |
| `--keep-size` | 关 | 最终 tile 保持处理尺寸，不缩回原图尺寸 |
| `--analyze-model` / `--image-model` | 见下 | 覆盖模型名 |

产出（`-o` 目录下）

| 文件 | 内容 |
|---|---|
| `tile.png` | **最终四方连续单元**，拿去印花的就是这张 |
| `preview_3x3.png` | 3×3 平铺预览，肉眼查接缝 |
| `compare.png` | 原图平铺 / 纯算法 / 本次结果 三方对比 |
| `to_edit.png` | 送进模型的待修补图（接缝已推到中央十字） |
| `mask.png` | 中央十字带 mask |
| `model_output.png` | 模型原始输出（未经还原，用于复盘模型干了什么） |
| `report.json` | 全部指标 + 诊断结果，可审计 |

## 三、接缝体检指标

| 指标 | 回答的问题 | 最佳值 |
|---|---|---|
| `boundary_error` | 对边像素差多少 | 0 |
| `seam_visibility` | 平铺后接缝会不会跳出来 | 1.0（接缝带梯度 ÷ 画面内部） |
| `ghosting` | 边缘带有没有被抹糊、重影 | 1.0（<0.8 判定重影） |
| `sharp_keep` | 接缝带的细节有没有被弄丢/弄多 | 1.0（<0.85 糊了，>1.30 多了） |
| `covered_ratio` / `white_ratio` | 有纹理面积 / 空白面积占比（地比例） | — |
| `fidelity.core_diff` | 最终 tile 相对原图改了多少（**看这个，不是看模型原始输出**） | 越小越好，>8 说明被重画 |
| `fidelity.correlation` | 花型主体结构有没有变 | >0.97 |

> 注意：`fidelity` 报的是**最终交付的 tile**，不是模型原始输出。
> 模型原始输出通常很难看（它总想整张重画），但那不是交付物 —— 交付物已经过 `compose` 还原。

### 为什么 `sharp_keep` 必须是独立指标

`seam_visibility` 和 `ghosting` 的分母都是**当前这张图自己的内部**，
所以它们的绝对值跨图不可比：留白图的边缘天生比画面内部空，比值天生远离 1
（实测能到 0.5），"偏离 1 多少才算坏"没有统一标准。

`sharp_keep` 的分母是**同一块区域修补前的样子**，内容逐像素对齐，
所以 1.0 有绝对含义 —— 就是"没动过"。这是唯一一个能跨图比较的指标。

它也是踩坑踩出来的：第一版打分为 `seam_visibility` 设了 20 的权重，
在深底密集花卉上把**肉眼明显更干净的模型结果判输了** ——
模型在接缝上补了几朵小花，带内梯度抬高 → 被判成"有硬边"；
而纯算法把带内抹平、值掉到 0.81 → 反倒像是"很干净"。现在权重压到 4，
只兜真正的硬边（>2），主判交给 `ghosting` 和 `sharp_keep`。

### 输入体检（probe）

**花钱之前先量一遍。** 判断"这张图能不能靠补缝修好"是可测量的，不用问模型 ——
补缝法的隐含前提是：图内部是好的，只有被切开的边缘是坏的，而且窄带里的改动
能被周围纹理**掩盖**。所以只看两件事：有多少材料可以拿来遮掩，以及补缝区
有多少会落在"没有纹理可藏"的地方。

| 字段 | 含义 |
|---|---|
| `textured_ratio` | 有纹理面积占比（地比例的分子） |
| `blank_ratio` | 空白 / 干净底色占比 |
| `ground` | 清地 <40% ／ 混地 40~60% ／ 满地 >60% |
| `baseline` | **实测**跑一遍纯算法得到的成绩（不是估算） |
| `route_hint` | `model` ／ `pure-algorithm` ／ `reject` —— 是建议，不是命令 |
| `warnings` | 要转述给用户的话（比如"留白占 45%，接缝会落在空地上"） |

阈值都在 `probe.py` 顶部：`BLANK_HEAVY=0.40`、`TEXTURE_THIN=0.25`、`TEXTURE_EMPTY=0.03`。
另外有一条**省钱规则**：纯算法已经到「优」且 `sharp_keep ≥ 0.95` 时，
即使地比例支持补缝也改判 `pure-algorithm` —— 没必要时不花那次模型钱。

`route_hint` 只用来在卡片上给建议，**最终走哪条路由质量闸门定**：
两条路都跑出来，谁评级高用谁。实测两张样本正好落在相反两档 ——
深底密集花卉 有纹理 96% / 留白 0% → `model`；
花框花卉 有纹理 52% / 留白 45% → `pure-algorithm`。

## 四、网关接口契约（实测确认，别想当然）

默认**一个网关两用**（出图 + 诊断同走一家，一把 key 全包）：

| 线 | 默认网关 | 默认模型 | 干什么 |
|---|---|---|---|
| 出图 | `https://api.apimart.ai/v1` | `gpt-image-2.5-flare` | 按诊断结果重绘中央十字带 |
| 诊断 | `https://api.apimart.ai/v1` | `deepseek-v4.1-flash` | 看图判断图案类型与接缝问题，只出文字 |

**也可以拆成两条线**，网关和 key 各走各的（比如诊断用 DeepSeek 官方降成本）：
同时给 `--analyze-base` + `--analyze-key` 才生效 —— 只给 base 不给 key 是无效的，
因为那会拼出"诊断 base 指到 A 家、key 却是 B 家的"这种必然 401 的组合。
只给一个 `--key` 就整条落回单线。认证统一是 `Authorization: Bearer <key>`。

### 对话（诊断）`POST /chat/completions`

- 默认返回 **SSE 流式**，必须显式传 `"stream": false` 才拿得到普通 JSON
- 图片按 `{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}` 传
- deepseek 这代是推理模型，`reasoning_content` 也占 `max_tokens`，要给足。
  额度不够时会**推理把额度吃光、content 直接为空**，所以代码里发现空就抬额度重试
- 模型 id 因网关而异。有一家官方只有 `deepseek-flash` / `deepseek-v4-pro`，
  其中**只有 `deepseek-flash` 支持图片输入**（另一个是纯文本，选了直接失败）

### 出图 `POST /images/generations` → 轮询 → 取图

**两版契约都支持，按响应形状自动识别** —— 换网关不用改代码：

| | A 版（ApiMarket） | B 版（APIMart） |
|---|---|---|
| 提交返回 | 顶层 `{"id": "image_xxx", "status": "queued"}` | `{"data":[{"task_id":"xxx"}]}` |
| 轮询 | `GET /images/{id}` | `GET /tasks/{task_id}` |
| 终态取图 | `result.image_url` | `result.images[0].url[0]` |

**坑一：尺寸有的网关锁、有的不锁。** 锁的那种（如 ApiMarket 的 `-1k` 档）
只吃下面这几档，多一像素都回 400（实测 1280x1280、1536x1536、1152x896、
1024x640、1024x2048 全被拒）：

```
1024x1024   1280x1024   1536x1024
1024x1280   1024x1536   1024x768    768x1024
```

规律是"**必须有一条边正好是 1024**"。APIMart 不锁，只要求"16 的倍数 /
总像素够 / 比例 ≤ 3:1"，`832x816` 这类直接能用。
所以吸附**按网关决定**（`APIMart.size_locked`，按主机名判断，
`pipeline` 只在这个标志为真时才 `snap_size()`）——
不该锁的锁上去反而会平白拉伸一下、白丢清晰度。
**纯算法路线永远不吸附**：本机确定性计算，没道理受网关的尺寸规矩约束。

**坑二：有的渠道不支持遮罩。** ApiMarket 的图片模型都走 Nexhina 渠道，
带 `mask_url` 一律回 400「暂不支持遮罩编辑」。代码会自动去掉遮罩重试，
并把结论缓存住（后续请求不再白发一次）。APIMart 支持遮罩。

但要留个心眼：**渠道"支持遮罩"不等于模型每次都守**。实测同一模型同一图，
带外改动从 7 到 68 都出现过（守规矩时 0~8，放飞时几十）。所以**别把保真寄托在
遮罩上** —— 带外像素一律由 `compose()` 强制还原，这才是保真的真正来源。

**坑三：结果图的 CDN 按 UA 拦人。** 下载地址挂在 Cloudflare 后面，
Python 默认的 `Python-urllib/3.x` 直接吃 **403 error code: 1010**
（浏览器完整性检查），必须带浏览器 UA。不加就永远下不到图，
而那个 403 看起来特别像"key 没权限"，能白查半天。

**坑四：IPv6 慢到像坏了（一次能白等 5 分钟）。** 同一个 CDN 主机解析出来
AAAA 排在 A 前面，而这台机器到 Cloudflare 的 **IPv6 是「连得上但极慢」** ——
不报错、不超时，就是慢：

| 同一张 562 KB 的图 | 耗时 | 速度 |
|---|---|---|
| 走 IPv6（urllib 默认挑的） | 152 秒 | 4 KB/s |
| 走 IPv4 | 2.6 秒 | 209 KB/s |

**跟代理无关**（`scutil --proxy` 里根本没配代理，是地址族的选择问题）。
`curl` 没事是因为它有 Happy Eyeballs（并发探两族、先通先用），
而 **urllib 没有**，它按 `getaddrinfo` 的顺序连第一个，于是每次都踩 IPv6。
一次四方连续要下 2~3 张图，光这一项就能拖掉 5 分钟。

解法见 `apimart.py` 的 `_v4_first_socket()` + `_V4First*Handler`：
把 IPv4 排到地址列表前面。**不是禁用 IPv6** —— 同族内部保持原序，
IPv4 全失败时仍会退到 IPv6，纯 v6 环境照样能用。

排查提示：这种情况**只看"通不通"是发现不了的**（HTTP 200、字节数也对），
必须比对**耗时**。判据是拿 `curl` 下同一个 URL 对一下速度 —— 差一个数量级
就说明是客户端选路问题，不是网络或网关问题。

### 评分为什么要不对称地罚「保析度」

同一张图，模型路线在**无遮罩**渠道上保析度跑到 1.4~1.5（整图重绘、给接缝带
补了真内容），纯算法因为羽化掉到 0.7。原来对偏离 1 是**对称惩罚**，
结果算出来"模型输给纯算法"、退回了纯算法 —— 而三联对比里能直接看到
纯算法那版的规律重影。现在「变多」只按 1/3 罚（见 `_sharp_penalty`）：
细节被抹掉（<1）是羽化重影，最坏；细节变多（>1）通常是在补内容。
回归验证：有遮罩的旧样例结论**完全不变**，只有无遮罩这一档被纠正。

## 五、代码结构

```
run.py                命令行入口（给人用的）
sifang/
  service.py          对外服务入口（给主程序按子进程调用，见第六节）
  probe.py            输入体检：地比例 / 留白 / 纯算法基线 → 该走哪条路线
  pipeline.py         编排
  io_utils.py         读写、尺寸规整、平铺拼图、data URL 打包
  seam.py             位移 / mask / 羽化 / 强制还原 / 边界对齐（纯算法）
  metrics.py          接缝体检指标
  apimart.py          网关客户端：诊断线 + 出图线（两版出图契约自适应、IPv4 优先）
tools/                复盘用的一次性脚本（不参与主流程）
  compare_routes.py   把两条路线都还原出来做肉眼对比
  make_report.py      生成自包含 HTML 报告（图片 base64 内嵌）

  metric_probe.py     各统计量判别力的对照实验
```

> `tools/` 里的脚本都要带 `PYTHONPATH=. ` 运行，例如
> `PYTHONPATH=. python tools/compare_routes.py inputs/x.jpg out/x`。

## 六、对外服务入口（给主程序调用）

主程序不 import 这个包，只按子进程调用 `sifang.service`。
契约只有两条命令，**改动必须向后兼容**：

```bash
python -m sifang.service probe -i 图.jpg --json-out 结果.json
python -m sifang.service run   -i 图.jpg --outdir 出图目录 --json-out 结果.json \
       [--key K] [--analyze-key K] [--base-url U] [--analyze-base U] \
       [--image-model M] [--analyze-model M] \
       [--no-model] [--candidates 2] [--band 0.12] [--align-band 0.03] [--sharp-band 0.08]
```

| 约定 | 说明 |
|---|---|
| 结果 | `--json-out` 指向的文件里是一个 JSON 对象，**永远有 `ok` 字段**；失败时 `{"ok": false, "error": "人话", "stage": "..."}` |
| stdout | 同一份 JSON 也打一份（方便手工跑） |
| stderr | 全部日志走这里，不污染结果 |
| 退出码 | `0` = 跑完了（业务失败也算，看 `ok`）；`2` = 参数错 |
| key | 出图 `--key` / `APIMART_API_KEY`，诊断 `--analyze-key` / `DEEPSEEK_API_KEY`；**不给 key 就自动只跑纯算法** |
| 双线 | 只给了出图 key 时，诊断自动沿用同一套（单网关），行为跟以前一致 |
| 自检 | 结果里的 `gateways` 段回报实际走的两个网关、是否分线、渠道支不支持遮罩 |

`probe` 是**零成本、秒级、不调模型**的：它只算地比例 / 留白占比 / 纯算法基线，
回答"这张图适合怎么走"。主程序拿它当提案卡上的体检结论。

`run` 的产物（`--outdir` 下）：`tile.png`、`preview_3x3.png`、`compare.png`，
以及中间件 `to_edit.png` / `mask.png` / `model_output.png` / `baseline.png` 和 `report.json`。

### 为什么要拆成子进程，不直接 import

PatternFlow 后端是**刻意零依赖**的（只用标准库，连 JPEG 解码都是自己调 sips + 自研解码器）。
这个算法要 numpy + Pillow，直接 import 等于把"要不要装第三方包"扩散到整个服务 ——
一次装坏，整个产品起不来。

所以拆开：算法带自己的 `.venv`，主程序只负责
「写临时文件 → 起子进程 → 读回 JSON」。算法环境坏了只影响这一个功能，
服务照常跑，报错也能报成人话；算法还能自己单独升级。

主程序那边的对接代码在 `后端/core/seamless.py`，技能在 `后端/skills/seamless_pattern/`。

**产物去向（用户明确要求）**：`tile` / `preview` / `compare` 三张图**不进花型库** ——
在 skill.json 里声明 `"ingest": false`，主程序按这个声明跳过自动入库。
那就必须留一个能拿走文件的出口：**点开大图，放大查看层里有「⤓ 下载」按钮**。
落盘本身**不覆盖**：同名时自动往后加序号（`-2`、`-3`…）。

## 七、已知边界

- **这张图适不适合平铺，是另一回事。** 工具负责"接缝接得对"，不负责"接了好看"。
  大面积留白的定位独幅、长笔触抽象图，即使接缝数学上完美，平铺出来也是另一种设计 ——
  诊断结果里的 `suitable` 字段会给出参考判断。
- 接缝落在**空白底**上时会显出一条浅带（没有纹理可藏），这不是算法误差。
- 羽化带必然带来轻微重影（`ghosting` 指标会报），想彻底消除只能缩小 `--mask-band` 让模型多干一点。
- **渠道能力决定补缝能有多干净。** 支持遮罩的网关能让模型只在中央十字带里动笔，
  带外几乎不变（实测带外改动 0~8）；不支持遮罩的渠道（ApiMarket 那几个都是）模型会
  整图重绘（带外改动 15~21），我们仍只取中央带拼回去，于是拼接边缘会糙一点。
  保真不受影响 —— 带外由 `compose()` 强制还原。**换网关前先看结果里的 `gateways.mask`。**
- **诊断模型必须能吃图。** 换成纯文本模型（比如 `deepseek-v4-pro`）会直接失败，
