# 全网搜花型

> 用户提出花型需求 → AI 分析需求 → **在全网搜真实存在的花型图** → 挑出对路的
> → 整理成和本地花型库一样的形状供挑选（默认 100 张）。

> ⚠️ **2026-10-19 起：取消四方连续检测标准。** `filters.tile_check=false` 时**完全不跑**接缝/纯色判定，
> 索引里 `tile_gate="skipped"`、`tile_quality=null`；排序里 `tile` 权重=0。
> 平铺判定仍保留为**单独工具**：`run.py tile <图>` / `run.py one <url>`（想恢复整条产线检测，把 `filters.tile_check` 改 true）。
>
> ⚠️ **2026-10-18 起：接缝不再当筛选条件。** 用户明确要求"接缝对不上不用做筛选"，
> 所以现在 `fetch` 默认**照收**铺不开的图。这个开关在 **`config.json` 的
> `filters.tile_gate`**（写 `true` 回到旧行为），临时想严一次就加 `--tile-gate`。
> 判定照跑、指标照记：索引里 `tile_gate: "on"` = 真能四方连续铺开，
> `"off"` = 接缝对不上（铺开会露缝，**别当可印花素材用**）；排序也把它们放后面。
> 仍然会被拦的只有两种"图本身没法用"：最短边 < 200px、整张纯色
> （后者也能用 `filters.drop_flat` 放开）。

## 零、本地怎么用（最短路径）

第一次用：双击 **`安装.command`**（建 `.venv`、装 Pillow，一分钟）。
之后每次：**双击 `搜花型.command`**，按提示回答三句：

```
选路线 [1/2]: 2
需求: 国风 花卉 水彩
输出目录: ↩
```

**所有产物都在 `产物/` 一个文件夹里**（不填目录名就自动给一个
`产物/out_1017_1546`，按时间命名）：

| 文件 | 是什么 |
|---|---|
| `产物/out_xxx/_gallery.html` | 画廊页，自动打开，可逐张看图 + 机器判词 |
| `产物/out_xxx/orig/` | 原图（挑中的直接从这拿） |
| `产物/out_xxx/index.json` | 索引，字段和本地花型库一致 |
| `产物/out_xxx/rejected.json` | 被剔的图和理由（语义甄别 + 相似去重都记在这） |
| `产物/out_xxx/_run.log` | 这一轮的完整日志 |

**不用买任何 key**（百度/360 图片免 key；对话与识图模型复用主程序已配好的那个）。

想自己拼参数（换模型、严判工艺、给已有目录补图）就用命令行，见第四节。

```
用户的一句话
   │
   ├─① wsearch/analyze.py    用大模型把需求翻成**一组能命中平铺图的检索词**
   │                         （中英各半，主动排掉"连衣裙/模特"这类招成品照的词）
   │
   ├─② wsearch/providers.py  多家来源**并发**搜，收图片直链（按来源轮流取）
   │                         （默认跑免 key 的百度 / 360 / 花瓣 / 堆糖 /
   │                           瓦栏 / 色彩跳动 / 全球纺织网 / Pattern Designs）
   │
   ├─③ wsearch/fetch.py      并发下载 → 内容去重 → **逐张跑平铺判定**，只留铺得开的
   │                         不够 100 张就自动翻下一页再捞一轮（最多补两轮）
   │
   ├─④ wsearch/screen.py     语义甄别：不是图案本身 / 和需求对不上 → 剔
   │
   ├─⑤ wsearch/similar.py    **相似只留一张**：同一张图换了尺寸/水印、
   │                         同一套素材的几个变体 → 留质量最高那张
   │
   ├─⑥ wsearch/rank.py       按平铺质量排序 + 感知哈希去重 + 压住单一来源垄断
   │
   └─⑦ wsearch/store.py      落成花型库形状：orig/ thumb/ index.json
```

### 两条路线：**凑数**还是**宁缺毋滥**

同一条产线、同一套闸门，只差一件事 —— **合格图不够时还翻不翻页**：

| | 路线 1 `search` | 路线 2 `pick` |
|---|---|---|
| 目标 | 交满 `--want` 张（默认 100） | **不设目标**，`--want` 只是上限（0 = 不限） |
| 不够怎么办 | 翻下一页再捞，最多 `--rounds` 轮（默认 3） | **不翻页**（默认 rounds=0），剩几张交几张 |
| 产出 | 100 张（凑不满就报差多少） | 这一轮筛出多少就是多少 |
| 一轮耗时 | 8~13 分钟；凑满 100 张常要 20~50 分钟（含换词重跑） | **8~13 分钟，一轮结束** |
| 质量 | 最后那几十张明显掉一档（第 7~9 页基本只剩"颜色像、做法不对"） | 齐整 —— 全是第一轮就筛出来的 |
| 什么时候用 | 点名"给我 100 张"、要铺满一个选款页 | 只在乎"每张都得对"，有多少算多少 |

路线 2 不是"少做一步"，是**换了个取舍**：宁可只有 40 张，也不拿 60 张凑数的
把合格的那 40 张稀释掉。两条路线的产出都会在 `manifest.json` / `index.json`
里记 `route`（`full` / `pick`），事后一眼能分清是哪条落的。

## 一、要买什么 key？—— **一个都不用买**

| 用途 | 要不要 key | 说明 |
|---|---|---|
| **① 全网图片搜索** | ❌ **不用** | 用的是**百度图片**和 **360 图片**的公开接口，免 key、免注册、开箱即用。见第二节。 |
| ② 需求分析（话 → 检索词） | ❌ 不用 | **复用主程序已经在用的对话模型**（DeepSeek 等）。不配也能跑，会退化成"关键词 + 行业词模板"。 |
| ③ 平铺判定 | ❌ 不用 | **纯本地算法**，不需要任何模型、不需要 GPU。见第三节。 |
| ④ 给搜回来的图打四维标签 | ❌ 不用 | 可选。真要打，用项目里已经有的 `算法/自动打标签`（本地 Qwen3.5-4B）。 |
| ⑤ 语义复核（可选，见第三节末） | ❌ 不用 | 用现成的识图模型即可，不用另买。 |

**一句话：不用买任何 key，装上就能跑。** 唯一值得配的是**对话模型**
（它的 key 主程序里本来就有）—— 配了以后检索词是模型按需求拟的，
比模板拼的准不少；不配也能出图。

## 一点五、配置文件 `config.json` —— 模型 / 爬虫目标 / 筛选项都在这

跟 `run.py` 同一层有个 **`config.json`**，改它就能管三件事，不用碰代码：

| 段 | 管什么 | 典型用法 |
|---|---|---|
| `ai` | **模型地址和 key**（对话模型 = 拟检索词；视觉模型 = 看图复核） | 换成自己的 OpenAI 兼容服务；比主程序配的那套更便宜/更快 |
| `crawlers` | **加减爬虫目标**：`disabled` 关掉哪几家，`custom` 加一家新站 | 这次不想让百度拖慢速度；或者发现一家新素材站想加进来 |
| `filters` | **筛选项开关**：接缝筛不筛、语义甄别开不开、相似去重开不开、最小边、纯色丢不丢 | 想要"多给点、我自己挑"就把 `tile_gate` 和 `similar` 关掉 |

**优先级：命令行参数 > 环境变量 > `config.json` > 代码默认值。**
也就是说：文件是"日常设置"，临时想变就加参数（不会把文件改脏）。

```bash
# 改完想确认生效没有
python run.py keys
# → 配置：…/config.json；关掉 2 家（baidu、so360）；接缝筛选=关；语义甄别=开；相似去重=开
```

几条设计上的取舍：

- **没有这个文件也照跑**（全用默认值）；JSON 写坏了只打一行警告，当没有配置；
- **字段可以只写想改的那几行**，没写的走默认；
- 手滑写成 `"false"`（字符串）、把数字写成 `"0.98"` 都能认 —— 手改 JSON 太容易这样；
- 模型 key 建议留空、用 `api_key_env` 指环境变量（**别把 key 提交进仓库**）；
  真要直接写也行，环境变量会**优先于**文件，临时换 key 不用改文件；
- 想让程序完全忽略这个文件：`WSEARCH_NO_CONFIG=1`（测试里就是这么隔离的）；
  想用另一份：`WSEARCH_CONFIG=/path/to/xxx.json`。

### 加一家新站（`crawlers.custom`）

配置里写几条正则就能加，**不用改代码**（只适合"服务端渲染 + 图直链在 HTML 里"的站，
JS 渲染/要登录/要签名的站它抓不到）：

```json
{
  "name": "mysite",                  // 唯一英文名，会出现在 --provider 里
  "label": "某素材站",
  "list": "https://mysite.com/search?q={q}&page={page}",
  "item": "<li class=\"card\">(.*?)</li>",   // 切卡片；不给就整页当一个块
  "img":  "<img[^>]+src=\"([^\"]+)\"",        // 抽图直链（必须有捕获组）
  "title": "<h3[^>]*>(.*?)</h3>",             // 可选：抽标题
  "pages": 1, "per_page": 30,
  "referer": "https://mysite.com/",
  "encoding": "utf-8"
}
```

规则：`{q}`/`{page}` 会被替换；卡片与标题正则**按跨行匹配**（HTML 天然多行）；
`//cdn…` 会补成 https、`/img/x.jpg` 会按 `list` 的域名补全；`"enabled": false`
就只当模板不跑（文件里那条例句就是模板）。写完 `run.py keys` 里能看到它，
`--provider mysite` 也能单独点它。

## 一点六、2026-10-19 大改：来源图 / 质量排序 / 溯源

用户给的目标：**快速、精准地获取内容高质量的图**；质量优先级
**符合需求 > 内容新 > 尽量多 > 画质尽量高**。这一轮加了四层：

### 1) 来源图（`wsearch/sources.py`）

把"从哪拿图"从 `providers.REGISTRY` 的一个 `kind` 拆成独立来源表：

- `CORE`：已接的来源（瓦栏/色彩跳动/全球纺织网/Spoonflower/patternbank/…），
  每家带 `kind`、`quality`（0~1 质量先验）、`lang`、`intents`；
- `SITE`：只能通过 Google/Bing `site:` 访问的精选站（Etsy、Creative Market、
  Creative Fabrica、Behance、Dribbble、品牌壁纸、日本插画素材站…），
  需要 Serper/SerpAPI/Brave 任意一把 key，用 `--provider site_search --sites ...` 手动开；
- `INTENT_BONUS`：business / inspiration / specific 三种意图下来源权重不同。

看清单：`python run.py sources`。

### 2) 新来源：CLIP STUDIO ASSETS（默认开）

日本插画素材平台的公开 JSON 搜索接口；一条返回 `material_id/name/thumbnail_url/
purchase_count/clip_user_handle`。中文/英文检索词会先过一小张日文词表
（小碎花→小花柄、水彩→水彩、无缝→シームレス…），否则日文站经常 0 条。
`purchase_count` 直接当热度信号进排序。

### 3) 排序：来源 + 新鲜 + 平铺 + 画质

`rank.WEIGHTS` 默认：

```
source 0.38 + fresh 0.24 + tile 0.00 + graphic 0.10
+ res 0.14 + provider 0.07 + engage 0.07
```

- `source`：来源类型 + 意图匹配（交易平台/作品集/品牌 > 通用搜索 > 图库）；
- `tile` 已置 0（取消四方连续标准），不再按平铺质量排序；
- 来源多样性：单 provider ≤22%、交易平台（marketplace）≤70%，剩下的名额给搜索/社区/插画/品牌；三段 strict→soft→fill 补满。
- `fresh`：发布时间（90 天内满分，3 年降到 0.35；没有日期按 0.5，不硬判）；
- `res` 只占 0.08 —— 用户明确说画质不是第一位；
- `engage`：商家侧热度（销量/收藏），没有就 0.5。

改权重：`config.json` 的 `quality` 段。`fresh_days > 0` 时直接过滤老图。

### 3.2) 验收收紧（2026-10-20）

用户指出多格预览、展示海报、布料拼拍、72px 博客缩略图、白边截图混进来了。
现在有三道**不依赖平铺检测**的硬闸门：

- `filters.quality_gate=true`（`config.json` 默认开）
- 最短边 **<200px** 直接剔（72px 缩略图不再送 API）
- 标题命中 `合集/拼图/九宫格/色卡/预览/展示/目录/海报…` 直接剔
- 底部 20% 几乎纯白、顶部不是（截图/展示图留白）直接剔
- VLM 提示词明确：**多格不同花型的素材合集/商品预览必须 false**；
  布料实拍、画笔颜料、带其它物体、糊图也 false
- 硬闸门判死的图**不再送 API**，避免模型又把 false 判回 true

这轮复筛：70 张 → 56 → 43 → **36 张**，用户截图的 0035/0036/0049/0051/0053/0061/0062/0065 全部清掉。

### 3.1) 语义甄别：API 视觉模型（2026-10-19）

- 默认接 APIMart（OpenAI 兼容）：`base=https://api.apimart.ai/v1`，模型 `gpt-5.4-nano`
  （便宜、能看图；实测 2~4 秒/批，输出 JSON 稳定）。配置在 `config.json` 的 `ai.vision_*`。
- **不要开本地模型**：`run.py probe` 里"语义甄别没跑"就是没配 API；配了之后
  `pick/search/refill/screen` 自动走 API。
- `--loose`：不按工艺严判，只剔非图案/明显跑题；适合"要大量、别被一个工艺词砍光"。
- 模型调用失败不会删图：判不出来的图按"留下"处理，note 如实写。
- `screen` 统计里新增 `调用次数`、`耗时秒`、`prompt_tokens/completion_tokens/total_tokens`；
  成本可从 APIMart `GET /v1/usage?start=...&end=...&group_by=model` 按轮次精确查。

### 4) 溯源字段进索引

`store._make_item()` 新增：

```
src_domain / src_author / src_kind / src_quality / src_created_at
/ src_method / src_engagement / has_source / license
```

`has_source=false` 的图只能当灵感/线索；`license` 区分
`unknown / purchase_required / clip_studio_terms` 等。

### 5) 命令行

```bash
python run.py sources                      # 看来源图和先验
python run.py pick "国风 花卉" --intent business
python run.py pick "国风 花卉" --provider site_search --sites etsy,creativemarket
python run.py pick "国风 花卉" --fresh-days 365
```

`--queries` 默认从 8 提到 10（多召回）；`--intent` 不填由需求分析自动判。

> ⚠️ 版权/robots：`site_search` 走的是 Google 索引，不直接爬目标站；
> 但下载的图仍受原站条款/版权约束。`has_source=false`、`license=unknown`
> 的图不要当可交付素材。

## 一点九、2026-10-20 全免 key 实测

按用户要求：需要 key 的 7 家（Serper/SerpAPI/Brave/Pixabay/Pexels/Unsplash/site_search）
在 `crawlers.disabled` 里暂时关闭；22 个免 key 来源用 `--provider` 全部打开。

查询「水彩 小碎花 法式浪漫」实测：

- 300 候选 → 293 去重 → 277 送 API → 156 通过 → 146 最终交付
- 总耗时 **347.4s**：抓图 40.6s、API 甄别 79.0s、其余约 227.8s
- 以后一条命令打开全部免 key 源：`--all-keyless`（需要 key 的仍由 `crawlers.disabled` 关着）
- API 账单：**$0.037462**（70 批，187,196 输入 / 7,434 输出 tokens，`gpt-5.4-nano`）
- 搜索 API 费用：**$0**（全部免 key）

耗时大头是 Spoonflower 的 Cloudflare（约 96s）和 Patternbank，不是模型。

> 的图。实测连打十几次之后：搜"碎花 平铺 素材"回来的是电动绿篱机，搜"青花 花卉

### 瓦栏：搜的就是**在售花型**（免登录，但只管"线索"）

瓦栏（walanwalan.com）是国内印花花型交易平台。加它是因为它跟前面几家**性质不同**：
百度/360/花瓣/堆糖搜的是"网上有什么图"，瓦栏搜的是**平台在售的花型设计**，
所以命中平铺花型的比例明显高。

| 实测 | 数据 |
|---|---|
| 一页多少张 | **固定 100 张**（翻到第 7 页还是 100 张，没限流） |
| 要登录吗 | **搜索页 / 分类页不要**（服务端渲染的公开页）；**详情页要** |
| 搜索是真的吗 | `水墨` 与 `几何` 各 100 张，photo id **交集 0** |
| 中英文 | 都认（`floral` 也回 100 张）—— 所以不像花瓣/堆糖那样按语言跳过 |
| 一轮实测 | "水墨画元素 国风 花卉 平铺 印花" → 100 候选 → 落 **20 张**，**44 秒** |
| 图片尺寸 | **300×450**（列表页缩略图，带 `.jpg`；**去掉后缀 404**） |

**⚠️ 边界（这一段是给改代码的人看的，别越线）**

- 这些图是**平台在售的商品**（￥99~299/张，设计师原创、可做版权登记）。
  代码**只取列表页公开的缩略图**，够做检索线索和视觉甄别；**不登录、不碰原图**。
- 索引里保留了详情页链接（`src_page`）—— 用户看中哪张，去详情页**正版下单**。
- **别拿缩略图直接投产**：300px 做不了印花，它的价值是"告诉你这个设计存在"。

**一个坑：这站也按空格做与匹配，但比花瓣/堆糖更"严"**

| 检索词 | 结果 |
|---|---|
| `青花 四方连续` | **3 张** |
| `水墨 印花` | 100 张 |
| 乱词 | 0 张 |

所以不能像花瓣那样"截到两词就停"——`青花 四方连续` 只有 3 张，得继续退。
`_walan_words()` 在 `_trim_for_zh` 的基础上**多退两档**：首词超过 4 个字时，
再补上前 4 / 前 3 / **前 2 字**当退路（`水墨画元素` → `水墨画` → `水墨`）。
循环里也不是见好就收，而是**留够 20 张才收手**，否则继续往宽的试。

> 标题要洗一遍：它的 `alt` 是模板拼的（`<分类标签>印花花型图片`），
> 一页 100 张里九十张都叫"年轻女装印花花型图片"。`_walan_title()` 把那截尾巴
> 剥掉，剩下"豹纹""中国风水墨"这种真标签 —— 不剥的话标题进索引等于没有。

### 色彩跳动：**接口是公开的 JSON**，比瓦栏还省事

色彩跳动（dancecolor.net，上海尚乎彩链）是国内**花型图案版权登记 / 侵权检测 /
交易**平台。它跟瓦栏同类（搜的都是**在售花型**），但实现路径完全不同：
瓦栏要解析服务端渲染的 HTML，它是 Vue SPA + 公开 JSON 接口 ——
**一个 POST 回 100 条，0.5 秒，不用浏览器、不用 cookie、不用登录**。

| 实测 | 数据 |
|---|---|
| 一页多少张 | **100 条**（`size:100` 实测有效，`pages` 算得对） |
| 要登录吗 | **不要**，匿名声明的接口直接 200 |
| 搜索是真的吗 | `水墨` 198 / `水墨 中国风` 14 / `几何` 494 / `四方连续` 85 / 乱词 0 |
| 一轮实测 | "国风 水墨 花卉 四方连续" → 60 候选 → **43 过平铺闸门** → 甄别后落 **13 张**，**31 秒** |
| 平铺闸门通过率 | **约七成**（搜索引擎那几家是 18~27%）—— 因为站里每条都是印花花型 |
| 图多大 | 站方图片处理出的预览，**长边 480**（原图 800~3500px，不下） |
| 额外信息 | 每条带 `fileWidth/fileHeight`（原图尺寸）和 `suitArea`（适用面料） |

**⚠️ 边界（比瓦栏那条更要紧，别越线）**

这个平台的主营业务就是**版权登记和侵权检测**，所以在它身上取图必须更克制：

- 只取**站方自己那套图片处理接口**出的预览图，**长边钉在 480** ——
  正好跟瓦栏列表页那档（300×450）一个量级：够看清平铺结构、够喂视觉甄别，
  但**当不了生产素材**。想"改大一点好用"的人先想清楚这条。
- 原图直链（`fileUrl`，实测 2.3MB / 2362×3543）**一次都不许下**。
- **不登录、不带账号**，`/api/worksInfo/*` 那些读写接口（`add`/`update`/
  `deleteById`/`vipDownloadFile`）**一个都别调** —— 只读 `getHomeInfoPage` 这一个。
- 索引里保留详情页链接（`src_page` = `.../#/detail?worksId=DC…`），
  看中哪张去正版授权。

**怎么找到接口的（前端换版本时照这条路再走一遍）**

这是个 Vue SPA，`robots.txt` / `sitemap.xml` 都回落到 `index.html`（等于没有），
首页只引一个入口包。接口藏在**路由分包**里：

```
assets/js/index-<hash>.js        路由表写死 → ./mallIndex-<hash>.js
  └ mallIndex-<hash>.js          → ./works-<hash>.js
      └ works-<hash>.js          api 定义：getHomeInfoPage: e=>o.post("/api/pageHome/getHomeInfoPage", e)
index-<hash>.js                  两个 axios 实例的 baseURL：x=/pb/crms、y=/pb/crbasems
```

**所以完整路径要加 `/pb/<微服务>` 前缀**：`/pb/crms/api/pageHome/getHomeInfoPage`。
少了这段就是 404（这个坑找了半天）。

**两个坑**

1. **搜索是整串 LIKE，不是分词**，而且**主语在尾巴上**：`法式小碎花` → **0 条**，
   而 `法式` 只有 5 条、`小碎花` **1838 条**、`碎花` 2159 条。
   瓦栏那套"从左边截"（法式小碎花 → 法式小碎 → 法式）在这里全落空，
   所以 `_dc_words()` 在它基础上**补两档**：
   **尾部截断**（`head[-3:]` / `head[-2:]`）+ **行业词单独试一条**（`四方连续`）。
2. **`worksTitle` 经常是系统拿 id + 标签拼的垃圾**：
   `DC170185027151453 时尚创意,节日,装饰纹样,动物,中国风 …`。
   `_dc_title()` 遇到"开头就是自己的 worksId / 带 `DC1` 前缀"的当垃圾丢掉，
   退回 `worksName`（那个才是作者填的标题）。

### 全球纺织网·花样画稿：**这一批里图最清楚的**

全球纺织网（tnc.com.cn / qfc.cn）的**花样画稿市场**（`hx.tnc.com.cn`）也是国内
面料印花的**花型交易平台**，跟瓦栏、色彩跳动同类，但它是三家里**图最大的一家**：

| 家 | 缩略图 | 一页 | 接口 |
|---|---|---|---|
| 瓦栏 | 300×450 | 100 | SSR HTML |
| 色彩跳动 | 长边 480 | 100 | 公开 JSON |
| **全球纺织网** | **600×900 无水印** | 24 | SSR HTML（GBK） |

URL 形状（换版时照这条路再走一遍）：

```
/search/products-c-<分类ID>-k-<GBK百分号编码的词>-p<页>.html
```

- `c` 是分类：**13773 全部** / 13774 女装 / 13775 男装 / 13776 童装 /
  13792 丝巾 / 13800 **碎花** / 13801 旗袍；
- `p` 是页码，首页 HTML 里的 `urlforma` 字段**直接写着这个模板**
  （`/search/products-c-13773-k-%CB%AE%C4%AB-p#.html`），不用猜；
- 还有个 `?attr_1614=5350/5351/5352` = 四方连续 / 二方连续 / 独幅 的筛选，
  但实测**单独加在关键词搜索上不生效**（要配合分类换），所以没用。

**三个坑**

1. **检索词必须 GBK 编码。** 按 UTF-8 编上去也回 **200**，但 `k` 参数被整段
   忽略 —— 拿到的是"全部 24 条"，连 `<title>` 都还是"全部花样画稿"。
   这个坑**只从"有没有报错"分辨不出来**，得比对卡片内容才发现。
   `_hx_word()` 显式 `encode("gbk")`。
2. **SSL 只认老套件。** 那台服务器只回 `TLS1.2 + AES128-SHA`（RSA 交换、
   没有前向保密、SHA1 做 MAC），Python 3.13 的默认 context 在 SECLEVEL=2 下
   把这套全禁了 —— 同一台机器上**curl 连得上、urllib 握手直接失败**
   （`SSLV3_ALERT_HANDSHAKE_FAILURE`）。解法是 `net.request(..., loose_tls=True)`
   给这一条链路单独降 SECLEVEL（**证书校验照旧开着**），见 `net.opener()`。
3. **并发会 500。** 同时打 4 个请求，第一页直接 Internal Server Error，
   串行就没事。所以 `_HX_GAP = 1.2` 秒。一页 24 条，要凑 60 张得翻 3 页 ≈ 4 秒。

**搜索是分词 OR，别照抄瓦栏的退让策略**：`水墨牡丹` 回 **32 页**，比 `水墨` 的
20 页**还多**（"牡丹"那一支也算了进来）；`碎花` 和 `花卉` 更是回**同一个 24 条**
（都命中"花"）。所以长词不会 0 条、不需要退让，但**长词更宽泛，不是更精准**。
`_hx_words()` 只给 `_trim_for_zh` 那两档。

**真正的价值在标签**：卡片上写着 `四方连续-花卉` / `中国风-水墨` / `花卉-水彩` /
`中国风-香云` —— 等于站方替我们做了一次"工艺 + 题材"分类，比任何搜索结果的
alt 都准。`_hx_title()` 把价格和作品编号剥掉，只留这截。

### Pattern Designs：接口很干净，但**图带满屏水印**（用户要求，已开成默认）

patterndesigns.com 是德国的**免版税矢量图案店**，2,100+ 一个分类，
整站都是四方连续。技术上它是最省事的一家（公开 JSON 接口、免登录）。

**三条硬伤**（本来因此被放进手动档；2026-10-18 用户要求开成默认，就都认了）：

1. **`gallery-m` 那档带满屏水印** —— "patterndesigns" 大字横在画面正中间，
   比瓦栏/色彩跳动那种"只是小一圈"差一档，只能当线索，不能像全球纺织网
   那样"看着就能用"。
2. **整站是硬边矢量平涂** —— 遇到「水墨 / 国风 / 扎染」这类**工艺**需求
   一条都对不上。实测（跟全球纺织网混跑）：33 张过平铺闸门、**甄别全剔**，
   理由清一色"硬边矢量插画，非水墨"。
3. **中文标题是机翻，语义会漂**：`水墨` 被它当成"**墨水**"（回墨水V形图案、
   墨水条纹），`国风` 回来的是一堆**大嘴鸟和法国斗牛犬**。

**它的正确用法是"按具体花名找"**，实测很准：

| 词 | 回来的 |
|---|---|
| `牡丹` | 精致的牡丹 / 小鸟和牡丹 / 冬季牡丹 / 日本牡丹 |
| `玫瑰` | 极简主义玫瑰花束 / 玫瑰园里的燕子 / 最后英国玫瑰 |
| `樱花` | 樱花时间 / 精致的樱花 / 欢快的樱花 |
| `竹` | 竹马赛克 / 竹之夜 / 竹灌木丛 |
| `碎花` / `青花` | ❌ 全混（这类词它没有，退化成"花"的全库） |

它现在**默认就在跑**；不想让它拖后腿，就用 `--provider` 只点别家。

**接口是怎么找到的**（这站是 Rails + 无限滚动，走的是明面上的路）：

1. 分类页 `/zh/gallery/<cid>/<名字>` 的 HTML 里就有分页端点的明文：
   ```html
   <div class="designs" data-scrollsize=60 data-ajaxloadmore=
        "/zh/search/ajaxLoadMoreDesigns/306?seoTitle=…&categoryId=306&sort=">
   ```
2. `application.js` 的 `context.loadMore` 读的正是这个 `data('ajaxloadmore')`，
   再往后拼 `&offset=N&limit=60`；
3. 返回 `{"designs":[{id, galleryImageUrl, designUrl, title, designer…}]}`。

**参数是试出来的，别猜**：

| 参数 | 结果 |
|---|---|
| `text=floral` | ✅ 生效（27 条，标题全是 Floral xxx） |
| `text=花卉` / `text=牡丹` | ✅ 生效（标题是站方机翻的中文，中文词能命中） |
| `q=` / `searchText=` | ❌ **静默无效**，回默认列表（看着像成功） |
| `?page=2` | ❌ **无效**，服务端照样回第一页；只有 `offset/limit` 能翻 |
| 乱词 | ✅ 回 `{"designs":[]}`，不报错 |

**两个跟别家相反的坑**：

- **行业词必须丢掉**（`_pd_words()`）。这站每条标题都是 `xxx 无缝矢量模式设计`，
  所以 `四方连续`/`无缝`/`平铺` 在这里**命中全库** —— 实测 `四方连续` 回来的是
  "虚线四足类""地理方块"，`国风 四方连续` 把"国风"整个淹掉。这跟瓦栏/色彩跳动
  要留行业词**正好相反**，别顺手"统一"。
- **别取 `detailImageUrl`** —— 那档只有 **400×400**，比 `gallery-m` 的 700×700
  还小（名字叫 detail，容易以为是"详情大图"顺手用上）。

### 源创花样网（ypattern）：**只能当线索图** —— 预览被裁过，全项目唯一的 `tile_opt`

ypattern.com 是 2015 年上线的**原创花样交易平台**，在售 10 万+ 款、服务端渲染、
免登录就能翻。`水墨` 自己有 **582 页**、`几何` 1837 页，货是真的多。

**但它过不了平铺闸门，而且没法绕：**

| 项 | 实测 |
|---|---|
| 缩略图 | **400×300**（4:3） |
| 卡片上的花回尺寸 | 20 张里 **12 张是 4488×4488（1:1）**，其余 3000×4488 / 5304×1894… |
| 结论 | **1:1 的花回被裁成 4:3 才给看** —— 拿到的不是整幅花回，接缝必然对不上 |
| 接缝比值 | 4.58 / 2.80 / 2.95（真平铺该在 1.0 附近，上限 1.55） |
| 首跑 | 60 候选 → **0 张**过闸门 |

这是站方**故意的防抄**（跟烧水印一个意思）。

**用户 2026-10-18 说"没关系可以用，只要符合标签就行"**，于是给它开了全项目
唯一的例外：`_item(..., tile_opt=True)` → `fetch.collect()` 里**不因为铺不开就丢**，
但会在记录上标 `tile_gate=False`、索引里写 `"tile_gate": "off"`。
**这批图只能当参考/线索，不能拿去印花** —— 后台和索引里能一眼分出来。

```
pick "国风 水墨 花卉 四方连续" --provider ypattern --candidates 40
→ 376 候选 → 下载 40 → **40 张全留下**（闸门放宽生效）→ 甄别 40 张全剔

pick "小碎花 复古 花卉 四方连续" --provider ypattern --candidates 40
→ **落 22 张**（剔 18），62 秒，索引里全是 "tile_gate": "off"
```

⚠️ 第一次全剔不是偶然，是它的**第二个毛病：检索词覆盖面极窄**。
实测（`记录总数` 是站方自己给的数）：

| 词 | 记录数 | 词 | 记录数 |
|---|---|---|---|
| `碎花` / `小碎花` | 9889 | `水墨` | 11624 |
| `玫瑰` | 104 | `复古` | 33 |
| `牡丹` / `青花` / `缠枝` / `团花` / `花卉` | **0** | `印花` | **198564 = 全库** |

也就是说：**它只认自己标签库里有的词**（碎花/玫瑰/复古这类），
国画花名（牡丹、青花、缠枝、团花）一个都搜不到；而 `印花` 这种行业词
**命中全库**（跟 Pattern Designs 一个毛病，喂进去只会稀释）。
所以用它要挑词：能用具体花名/风格词，别用国画术语。

三处技术细节（都跟别家不一样）：

1. **检索词必须 UTF-8，按 GBK 编上去直接 HTTP 500** —— 跟全球纺织网**正好相反**
   （hx 那边按 GBK 才对、按 UTF-8 是"静默回全库"）。两家一正一反，别互相抄。
2. **翻页是 ASP.NET WebForms 的 PostBack**：`?page=2` 完全不认（回第 1 页）。
   只能把上一页的 `__VIEWSTATE/__VIEWSTATEGENERATOR/__EVENTVALIDATION` 原样
   POST 回去，`__EVENTTARGET=AspNetPager1`、`__EVENTARGUMENT=<页号>` ——
   **只能一页页往下走，不能跳页、不能并发**（这条路是通的，能翻到 582 页）。
3. **一页 20 条，同一张 HTML 里还塞了 20 张"您可能感兴趣的花型"**（`#yourlike`，
   class 是 `column-four`）。只按 `/Preview/` 正则抓会**多抓一倍、全是噪声**，
   而且这些噪声在相邻页之间重复 —— 必须只认 `cbp-item designerli` 卡片，
   并且要求**编号 / 目录名 / 文件名三者一致**。

另外：卡片**没有标题**（只有编号、花回尺寸、价格；详情页 302 到 `join.aspx`
会员注册）；`robots.txt` 把 Googlebot / Bingbot / Baiduspider 等
**9 个搜索引擎逐个 `Disallow: /`**（没写 `User-agent: *`）—— 站方立场是"别抓"，
所以它**只读列表页、串行慢走、不进详情页、不碰原图**，也**不进默认**。
还有 `孔雀` 这个词稳定 **403**（`水墨`/`几何`/`大理石`/`碎花` 正常），像关键词过滤。

### Patternbulk：设计对象里**自带标题和 25 个标签**

patternbulk.com 是欧洲的**免版税花型交易平台**（原图 4000px / 300dpi 起）。
它最好的一点：列表页是 Next.js 的服务端渲染，**整个设计对象塞在 RSC payload 里** ——
标题、标签、原图尺寸、颜色、适用品类全都有：

```
{"id":"9db4c78a…","title":"Distressed Indigo-Plum Overdyed Plaid - Rotary/Digital…",
 "tags":["seamless","repeat","textile","fashion","screenprint","geometric",…],
 "image":"pattern_b6bbabae….jpg","folderId":"805dd6ed…","width":4134,"height":4134}
```

100 条里 **88 条带 `seamless` 标签**，题材标签有 `chinoiserie` / `botanical` /
`watercolor` / `floral`，等于站方替我们分好类了。

**两个硬限制（所以是手动档 `--provider patternbulk`）：**

1. 缩略图只有 **266×266**（`thumb_pattern_*.jpg`；原图 `pattern_*.jpg` **404**，
   要买）→ 只能当线索；
2. **没有服务端搜索**：`?q=` / `?page=2` / `?offset=` / `?search=` / `?tags=`
   **全部无效** —— 换任何参数都回同一批 100 条（实测三次请求 id 集合完全相同）。
   所以做法是：**取一批 → 按标题+标签本地打分 → 命中的排前面，筛不满就补到 12 条
   交给模型判**（用户要的就是这个用法）。全中文需求直接返回空，别硬凑。

**实测**（`pick "法式 中国风 花鸟 花卉 四方连续" --provider patternbulk --candidates 40`）：
**40 候选 → 31 过平铺闸门 → 甄别通过 21、不符需求 10 → 落 21 张，37.6 秒。**
人眼抽两张：一张灰底粉玫瑰的线描缠枝花卉（真四方连续）、一张深底亮色大花 ——
都是能用的参考图。266px 做不了印花稿，但"看对路"够了。

### 花瓣 / 堆糖的三个坑（都是实测踩出来的）

1. **长检索词一律 0 条。** 这两家把检索词按空格拆开做**与**匹配，词一多就没结果：

   | 检索词 | 花瓣 | 堆糖 |
   |---|---|---|
   | `法式小碎花 平铺 无缝图案 水彩手绘 粉彩花卉 四方连续 印花素材`（analyze 生成的原词） | 0 | 0 |
   | 截到 5 个词 | 0 | 0 |
   | 截到 3 个词 | 0 | 30 |
   | **截到 2 个词**（题材 + 行业词） | 9 | 30 |

   所以 `_trim_for_zh()` 把它们截成**第一个词 + 第一个行业词**（行业词决定回来
   的是不是平铺素材），还搜不到就退到只留第一个词。
2. **花瓣的直链要换域名 + 换 Referer，两件事都得做。** 这一步踩了两次，记清楚：

   | 组合 | 结果 |
   |---|---|
   | `gd-hbimg-edge.huaban.com`（API 给的） | **0/20**，HTTP 567 |
   | `gd-hbimg.huaban.com`（2026-10 之前 20/20） | 现在 **0/15**，`567 auth failed` |
   | **`hbimg.huaban.com` + `Referer: https://huaban.com/`** | **20/20** ✅ |
   | `hbimg.huaban.com` 不带 Referer | **567** |
   | `hbimg.huaban.com` + Referer = **具体 pin 页** | **567** |

   所以现在是：主链走 `hbimg.huaban.com`（**去掉 auth_key**，它不校验，少一个会过期的
   变量），下载时 **Referer 必须钉成站点根 `https://huaban.com/`** —— 这是 `_item()`
   的 `ref` 字段存在的唯一原因（其它站都默认用来源页，只有花瓣不吃）。
   API 原样那条 edge 直链塞进 thumb 当第二域名退路：它现在基本下不动，
   但万一 `hbimg` 也挂了，它是唯一的路。
3. **只认中文词。** 英文检索词在这两家基本是空的，代码直接跳过，省一次请求。

> 各家的结果在 `providers.search()` 里是**按来源轮流取**拼起来的（`_interleave`），
> 不是"百度全部在前"。下游会把候选截到 800 条再下载，按来源顺序拼的话后面几家
> **一条都进不了下载队列** —— 加了新来源等于白加。

> ⚠️ 这几家都是**没有承诺**的公开接口：同一分钟里连打几次会被临时挡回来
> （百度会回一页 HTML 而不是 JSON，必应会回一个 0 字节的空页）。所以代码里
> 对**每一条检索词**都做了"失败重试 + 单条失败不影响其他条"
> （`providers._with_retry`）—— 一家只丢一条词，不会把整批结果一起赔进去。

> 探过、**没接**的几家（都写在这儿，省得以后再试一遍）：
> · **搜狗图片**：`pic.sogou.com/napi/pc/searchList` 即使带 cookie 也回
>   `{"status":1,"info":"forbid","data":null}`，还要签名参数。
> · **Wikimedia Commons / Openverse / Yandex**：本机连不上（TLS 握手超时）。
> · **Met 博物馆**：v1 的 search 已在 2026-10-01 下线（HTTP 410），v1.1 能用，
>   但回来的多是"文物照片"不是平铺单元，还要两跳请求（search + object），不划算。
> · **站酷 / 千图 / 包图 / 摄图 / 花瓣网页版**：JS 渲染或 404，抓不到图直链
>   （花瓣要走 `api.huaban.com`，已接）。
> · **DuckDuckGo / Yandex / 头条 / 微博**：要么超时，要么返回里 0 条图。
> · **源创花样网（ypattern.com）**：能爬、能翻 582 页，但**预览图是把 1:1 的花回
>   裁成 4:3 给的**，60 张 **0 张**过平铺闸门 → **已按用户要求当「线索图」接入**
>   （全项目唯一的 `tile_opt`，索引里标 `tile_gate=off`，详见下面那节）。
> · **patterncooler.com**：连详情页和前端 JS 都翻过了 —— 免费预览**只有 120/180
>   两档**（`pCoolr.min.js` 里 `passSize` 只可能是 120 或 180），4000px 大图要
>   注册付费下载 → 用不上。
> 另外：Bing **图片 API** 已于 2025 年 8 月退役（现在用的是网页的 async 接口），
> Google **从没开放过**图片搜索 API。
>
> **专业花型站单独探过一轮**（用 Scrapling 的浏览器指纹打的，结论见「爬取专业
> 花型站」那节）：patternbank 成了（已接）；**spoonflower 403、colourlovers
> Cloudflare 拦截页**（这两个要上真浏览器，即 `StealthyFetcher`，暂不做）；
> **thepatternlibrary / subtlepatterns 是纯 JS 渲染**，HTTP 层拿到 0 张图，
> 同样要开浏览器；**freepik** 走系统代理时会被 curl 的 SSRF 保护拒掉
> （重定向到 127.0.0.1），**vecteezy** 的搜索页会 302 回首页。

### 爬取专业花型站（Scrapling，**可选依赖**）

上面几家都是"通用图片搜索"：搜回来的图**只有两成是真平铺**。专业花型站不一样 ——
**整个站就是四方连续的印花设计**，平铺闸门通过率会高一截。但这类站大多有反爬，
`net.py` 那套（urllib + 浏览器 UA）拿不下来：

| 站 | net.py 直连 | Scrapling Fetcher |
|---|---|---|
| **patternbank.com** | **403** | **200** ✅ |
| **spoonflower.com** | 403 | 403 → **浏览器层能过**，见下面「Spoonflower」 |
| colourlovers.com | 403 | 403（Cloudflare 拦截页） |
| thepatternlibrary.com | 200 但 0 张图（JS 渲染） | 200 但 0 张图（**要开浏览器**） |

关键差别在**TLS 指纹**：UA 是应用层的，改 UA 没用；这些站挡的是握手层的特征。
Scrapling 的 `Fetcher` 底层是 curl_cffi，能模拟 Chrome 的 TLS/HTTP2 指纹。

**怎么装**（不装不影响别的来源，只是这一家跳过）：

```bash
./.venv/bin/pip install "scrapling[fetchers]"
```

**为什么只用它的 Fetcher，不用浏览器。** Scrapling 还有 `StealthyFetcher` /
`DynamicFetcher`（真开 Chromium，能解 Cloudflare Turnstile），但那两个要
`scrapling install` 再下几百 MB 浏览器，而且一页 3~8 秒 —— 一轮十几条检索词，
慢不起。Fetcher 是纯 HTTP，**1~2 秒一页**，已经够拿下 patternbank。

#### Patternbank 实测（这几个数决定了它怎么用）

| 检索词 | 出图 |
|---|---|
| `floral` | 15 张 |
| `leopard` | 16 张 |
| `geometric` | 3 张 |
| `floral seamless pattern` | 4 张 |
| `indigo floral seamless repeat` | 6 张 |
| `花卉` / `碎花`（**中文**） | 各 22 张，**交集 22/22** —— 根本没按词过滤 |

三个结论，都写进代码了：

1. **只认英文词。** 中文词返回的是同一份"最新上传"列表（标题里混着
   `texture-leaf`、`zig-zag`），掺进来就是噪声。所以 `_pb_word()` 用
   `_cjk()` 反着过滤 —— 只吃英文检索词。analyze 生成的词本来就"中英文各占一半"，
   正好对得上。
2. **量小：一页 4~15 张，第 2 页就只剩 3 张。** 它是"小而精的补充"，
   别指望它凑数 —— 凑数还是靠百度/360/花瓣/堆糖。
3. **必须限速。** 间隔 <2 秒连打，第 4~5 次开始回 403。爬取层默认
   `GAP = 3` 秒（`scrape.py`）。

#### 爬取层的三条规矩（改的时候别破）

1. **`net.py` 仍是唯一网络出口。** 这一层只负责"取页面 / 取直链"，
   **下载图片一律走 `net.fetch_bytes()`** —— 出口策略还是只有一套。
2. **强制直连。** Scrapling 底层是 libcurl，**会读 `http_proxy`**；本机系统代理
   常年开着，实测有的站经代理会被重定向到 127.0.0.1，然后被 curl 的 SSRF 保护
   拒掉（`Redirect to internal IP 127.0.0.1 rejected`）。所以发请求前会临时摘掉
   `*_proxy`，发完放回（和后端起子进程时摘代理变量是同一个道理）。
3. **可选依赖不能变成启动期崩溃。** 全项目只有 `scrape.py` import scrapling，
   而且是**懒加载**（首次 `get()` 时才 import）。没装就 `have()` 回 False →
   这一家从可用列表里消失 → 跑起来直接跳过。

#### 想再加一个专业站

照 `providers._patternbank` 抄：**一个函数 + 一行注册**（`REGISTRY` +
`DEFAULT_ORDER`，需要 Scrapling 的话加 `"needs": "scrapling"`）。
解析别写通用爬虫 —— 每家的 DOM 都不一样，通用爬虫最后会变成一堆 if。

### Spoonflower：**能爬**（站方允许），但要过 Cloudflare

先纠正一个很容易搞错的判断：

> **Cloudflare 的 403 不等于"禁止抓取"。** 判断能不能爬，看 `robots.txt`，别看状态码。

它的 robots 原文（这段要过 CF 才拿得到）：

```
# Crawler blocking is enforced at the network edge (Cloudflare)
# ---------------------------------------------------------------------------
# Everyone else: crawlable, with content signals reserving training rights
User-agent: *
Content-Signal: search=yes, ai-input=yes, ai-train=no
Disallow: /fabric_items/  /product_information/  /api-gateway/  /graphql
Disallow: /*?*rd=   /*_rsc=   /proxydirectory/
Allow: /assets/  /intl/  /*.css  /en/designs/*/similar/*
Crawl-delay: 1
```

翻成人话：**通配 UA 可爬**；`search=yes`（建索引）和 `ai-input=yes`（喂 AI 做检索，
我们的视觉甄别就属于这一步）都允许；只禁 `ai-train`（我们不训练）。
**唯一的硬约束是 `Crawl-delay: 1`** —— 代码里真等了 1 秒。

| 实测 | 数据 |
|---|---|
| 搜索页 | `/en/shop?on=fabric&q=<词>`，**一页 121 张**，图就是印花设计本身 |
| CF 挑战 | `solve_cloudflare=True` 能解（`managed` + `embedded` 两种都要过） |
| 一页耗时 | **约 96 秒**（挑战占 80 秒）—— 所以它 `default=False` |
| 图片下载 | `img.spoonflower.com` **不走 CF**，直连即可 |
| 尺寸档位 | `/p/f/s`=100、`/p/f/m`=294、**`/p/f/l`=400**（xl/o 都退回 294） |
| 标题 | `alt` 是真语义标题（"Among Flowers" / "English Chintz Blue Pink"） |

三个坑（都踩过）：

1. **不要传 `network_idle=True`** —— 这类站的请求永远不空闲，会一直等到超时，
   实测整个进程被 SIGKILL(137)。用 `wait_selector="img"`。
2. **直链尾部必须有 `/<designId>.png`** —— 少这一段就全 404（拿到过 115 字符的
   "看起来完全正常"的版本，全部 404，找了好久）。
3. **用 `StealthySession` 复用浏览器**，别每个词新开一个 —— 每次 fetch 都重新过
   CF 挑战，一页 96 秒里 80 秒是挑战。

用法（默认不跑，要手动开）：

```bash
./.venv/bin/python run.py pick "chinoiserie floral" --provider spoonflower --want 30
```

> 400px 上限意味着它跟瓦栏一样是**线索级**：告诉你这个设计存在、长什么样，
> 真要投产得去站上买。但它一页 121 张、标题是语义的，做题材探索很顺手。

### 可选的补充：境外搜索代理 / 图库（要 key，**不配也照样跑**）

什么时候需要：百度/360 哪天被反爬挡死了，配一把境外代理就能顶上去；
或者你想要 Pinterest / Etsy 那类英文素材。**平时不配完全够用。**

## 三、平铺判定：这一节是这个算法的关键（不需要任何 API）

用户的要求里，"不管水印和清晰度"可以放宽，但**"必须是真正的平铺图"是硬条件**。
一张铺开就露缝的图进了库，只是让客户白挑一轮。所以这一层不是可选优化。

### 原理只有一条

真正的平铺单元，把它的**右边界和左边界放在一起应该是连续的** —— 它在原图案里
本来就挨着。于是算两个量：

```
接缝差 = mean|最右列 - 最左列|
常规差 = mean|第 i 列 - 第 i+1 列|      （图内部相邻列，全图统计）
```

然后看**比值**。这是尺度无关的 —— 深色花型和浅色花型的绝对差异差着好几倍，
但真平铺的比值都落在 1 附近。

### 两个把人坑惨的地方

**坑一：真平铺的比值是 ≈1，不是 ≈0。**
一开始按"接缝差应该接近 0"去想，结果把真图全判成假。后来用**合成图**（正弦干涉图，
数学上严格周期）标定才看清：接缝处本来就是一次正常的相邻列跳变。判据只能定成
"比值明显大于 1 就是接不上"。

**坑二：有些图根本不能靠比值判。**
相邻像素几乎不相关的图（噪点、高感光照片），接缝差和常规差都是同一个统计量，
比值恒等于 1 —— 无论它铺得开铺不开。所以必须再加一道**绝对上限**
（`EDGE_ABS_MAX`）：接缝差自身也不能太大。

### 被数据推翻的两个早期设计（记下来免得走回去）

- ~~最外圈标准差守卫~~：本意是拦"花型贴在白卡纸上的展示图"，结果把
  **居中单花 + 素底**这种最常见的合法平铺一起拦了（它的最外圈就是一片素色）。
  已删除。
- ~~纹理门槛 1.2~~：本意是拦纯色/渐变，结果把**稀疏花型**（大半张是素底）
  一起拦了。现在只保留"纯色"这一个极端值。

### 还差什么（**已知缺口，说清楚**）

合成实验（`tools/test_tile.py` 里那 20 组已知答案）证明了两类假图
在**纯几何特征上无法**和合法花型分开：

| 假图 | 和它长得一样的合法花型 |
|---|---|
| 花型贴在白卡纸上的展示图 | 素底上居中一朵大花 |
| 四周压暗的影棚打样照 | 深底上居中一朵亮色大花 |

实测数据：卡纸图的"四角与整体亮度差"是 +11~+16，而**合法**的"素底居中大花"
是 +47~+84 —— 合法花型的偏差反而更大、方向还一样。这个量分不开两者。

**这不是纸上推演，真跑一次就看得见**：拿"国风 青花 花卉"跑满 100 张，
抽查前 36 张里有 3~4 张是**深底上整齐排列的实物照片 / 3D 渲染**（一盘子鸡蛋、
贝壳之类）—— 它们排得规规矩矩，接缝比值天然≈1，几何闸门拦不住。
三类图在这几个量上的实测值：

| 图 | `corner_diff` | 说明 |
|---|---|---|
| 真·平铺花型（多数） | +5 ~ +21 | 正常 |
| 深底居中亮物（**误判的**） | **−13 ~ −48** | 四角比整体暗 —— 正是"四周压暗"那一类 |
| 素底居中大花（合法） | +47 ~ +84 | 四角比整体亮 |

方向和幅度都无法把"深底居中亮物"和"深底居中亮花型"分开，所以**没有为它加门槛**
（加了就会误杀深底花型）。当前策略是：它排在**中后段**（平铺质量/图形感都拿不满分），
真要清掉只能靠语义复核。

要拦住这一类，只能靠**语义甄别**：拿视觉模型问一句"这是花型图案素材，
还是实物照片 / 3D 渲染 / 贴卡纸的展示照"。项目里现成就有（后端配好的
`deepseek-flash`，跟需求分析同一个 key）。这一步已经接上了 —— 下一节就是它。

## 四、语义甄别：机器能判的交给模型，判完不够就补

平铺闸门只管"能不能铺"，它管不了"这是不是一块花型素材"。这第二刀由**视觉模型**
来切，切完不够 100 张就继续出去捞 —— 也就是：**删掉不合格的，再补齐**。

### 谁来判（默认走云端，快一个数量级）

**默认用后端已经配好的识图模型**（`后端/config` 里的 `vision.model`，没配就退
`llm.model`）。现在配的是 `deepseek-flash` —— 它本身就支持图片输入，跟需求分析
同一个 key、同一个端点，不用另开账户。

实测同一批 95 张（每张 768px）：

| 判官 | 耗时 | 判 100 张的墙钟 |
|---|---|---|
| 本机 Qwen3.5-4B（端口 11435） | 6~10 分钟 | 4~10 分钟 |
| **deepseek-flash（8 路并发、每批 10 张）** | **4.6 秒** | **约 5 秒** |

**快 75~125 倍**，而且是按批计费的固定开销占大头（6 张一批时 prompt 才 2017
token、输出 131 token，判 1000 张候选也就几毛钱）。

判词质量也差一档。同一张图：

- 4B：`靛蓝底不规则纹理` ／ 把「九宫格兔子」说成「单只居中留白」
- deepseek-flash：`16只简笔卡通兔网格` ／ `9只蝴蝶结卡通兔排列，四周白边`

**"判词串味"仍然存在**（同一批里会把上一张的判词套到下一张），提示词里已经
明写"每张单独看、不许同上"，但没根除 —— 所以判词只能当**线索**看，别当铁证。

要退回本机模型（图不出本机、零成本）：

```bash
算法/自动打标签/本地模型/启动本地模型.command     # 先起服务
--vlm-base http://127.0.0.1:11435/v1            # 再指过去
```

两边的**关思考链写法不一样**，写错了不报错、只是白等：本机 mlx 认
`chat_template_kwargs.enable_thinking=false`；DeepSeek 官方默认是**开着**
thinking + effort=high，得显式给 `thinking.type=disabled`。`screen.py` 按
端点地址自动选，别只写一种。

没配好也能用，只是少一道把关（几何判定照跑），结果里会**如实写明**这一层没跑。

并发和批大小**跟着引擎走**，不用手调：云端默认每批 10 张 + 8 路并发，本机默认
每批 6 张 + 单路（单卡上并发只会互相拖）。要覆盖就 `--vlm-batch` / `--vlm-workers`。

**云端会限流，已经内置退避重试。** 8 路并发连着跑几轮就会撞 429（"使用量已超出
频率限制"），`screen.py` 对 429/5xx/超时按 2、4、8、16 秒退避、最多重试 4 次。
不重试的后果很实在：整批判不出来 → 按"判不出来就留下"的规则，那几十张会**全部
无甄别入库**。抖动是按比例的（±25%），不是固定值 —— 8 路同时被限时，固定间隔
会让它们同时醒来再同时撞墙；但抖动幅度大于基础间隔又会让退避不再递增，两种写法
都试过，现在是按比例。

退避 4 次还过不去就**明确报"被限流"**，不会伪装成网络抖动让你白等。真撞上日额度
上限时（重置时间以小时计），换成 `--vlm-base http://127.0.0.1:11435/v1` 走本机
模型是最快的出路。

### 它判什么

| 维度 | 判什么 | 严格程度 |
|---|---|---|
| `pattern` | 这张图**本身**是不是一块花型图案素材 | 严：实物照、3D 渲染、模特上身、贴卡纸的展示照、截图海报 → 剔 |
| `match` | 画面主题跟这次需求**明显冲突**吗 | 松：只有明显跑题（搜青花出来人物/风景/皮革）才剔 |

两维**都是 true 才留**。实测 `pattern` 会偏松（3D 球体上贴着青花也被判"是图案"），
所以不能只看它。

**判不出来（模型没吐、超时、整批挂了）的图一律留下** —— 甄别是"多一道把关"，
不是"少了判词就当垃圾"。宁可让用户自己删，也别无声无息丢掉好图。

判不出来的还会**拆小重试一次**（6 张一批 → 2 张一批）。真机上跑 100 张挂过 10 张，
一查全是"两整批"——不是判不出来，是批量太大、模型把 JSON 写坏了。拆小之后 0 漏判。

### 用户点名了工艺/风格时（扎染、蜡染、水彩、刺绣…）：判据要换一套

这是被用户一句话逼出来的改动。搜「国风 扎染 风格的印花图案」，交出去 100 张，
用户的反馈是：**"大部分好像并不是扎染的"**。查下来是两层原因叠加：

1. **需求分析根本没跑**。那一次的 `engine` 是 `template` —— 检索词只有
   「原话 + 无缝平铺」，`shibori`、`tie dye`、`indigo resist`、`扎染晕染`
   这些工艺词一个都没有。搜索这一层就已经带偏了，回来的是"靛蓝色系图案"，
   蓝印花布、佩斯利、曼陀罗、青花、水彩全在里面。**同色系 ≠ 同工艺**。
2. **`match` 这一维当初刻意设成"松"**（只防明显跑题：人物/风景/食物）。
   风格需求问的不是"跑题与否"，而是"做法对不对"，判据完全不同 —— 宽松版一律放行。

所以现在：需求分析会额外抽出 `craft`（工艺名）和两组**画面上看得见的**正反例
（`style_pos` / `style_neg`），交给甄别当判据；`match` 随之转严。同一个需求抽出来的是：

```
craft: 扎染
正例：不规则晕开的同心圈纹与色斑 / 颜色互相渗开的柔和软边 /
      捆扎折叠留下的放射状折痕 / 靛蓝底上留白、深浅不匀的手染斑块
反例：规整的格纹菱形条纹几何 / 佩斯利腰果花、曼陀罗式对称放射 /
      蓝印花布那种硬边漏印、版画式平涂 / 电脑矢量扁平插画 / 水彩写实花卉
```

**反例写在正例前面**（先排除、再确认）。顺序反了会出怪事：真机上见过
判词写着「蓝白扎染**硬边漏印**」却给了通过 —— 它自己都说硬边漏印了，
那正是反例清单第一条。改成先排除之后这类自相矛盾的判定基本没了。

三个数字说明这套判据值多少（同一批 100 张、同一个模型、都跑两遍对比）：

| 判据 | 通过 | 剔除 | 肉眼一致度 |
|---|---|---|---|
| 宽松（只有"明显跑题才剔"） | 90 | 10 | 差：一多半是"颜色像、做法不对" |
| 严（工艺正反例） | **27** | 71 | 好：被剔的理由对得上（佩斯利/曼陀罗/蓝印花布/矢量插画） |

**送审分辨率别再往上调**。试过 1024：判词退化成清一色"扎染扎结晕染纹理"，
反而把**明确是扎染的**泼染条纹判死了（假阴性）。768 是这批图的甜点。

想自己写死几条判据（机器判偏了的时候）：

```bash
./.venv/bin/python run.py refill ... \
  --craft 扎染 \
  --style-pos "晕染圈纹,颜色互相渗开的软边" \
  --style-neg "佩斯利腰果花,曼陀罗对称放射,蓝印花布硬边漏印"
```

判据会跟着落进 `index.json` 的 `need.craft / style_pos / style_neg`，
下次 `refill` / `screen` 直接沿用，不用重抽 —— 补图时换了判据最危险：
老图按老判据留、新图按新判据进，两边不同源。

> 说清楚剩下什么：本地 4B 判"蓝印花布 vs 扎染"这种细微差别，100 张里仍有
> 五六张会放过（多是有布纹的实拍、或者硬边但配色极像的）。这不是提示词能
> 再挤的，是模型能力边界。剩下的靠 `refill` 循环收敛：你再删几张，它再补。

### 一条命令做完"删 + 补"

```bash
./.venv/bin/python run.py refill "国风 青花 花卉 平铺 无缝 面料印花" --want 100
```

它会：① 先甄别目录里现有的图，不合格的剔掉；② 数一下还差几张；
③ 缺就重新检索补齐（新图同样要过"平铺闸门 + 语义甄别"，不够还会自动翻页），
④ **追加**落库。

两个只想做一半的场景：

```bash
./.venv/bin/python run.py screen --outdir out      # 只甄别，不补
./.venv/bin/python run.py refill ... --no-rescreen # 只补，不重新甄别
```

你自己在 Finder 里删掉几张不满意的图，再跑 `refill` 就是补齐 ——
**已有图的编号一个都不会变**（编号只增不复用，删掉的号也不会被新图捡走）。

### 被剔掉的图留档

```
out/rejected.json    每条的理由（"3D球体试贴图""皮革纹理非青花"…）+ 来源站 + 原页面
out/_rejected/       被剔的缩略图
```

留档是有意的：**甄别删错比漏删更难发现**。用户扫一眼就能知道机器判得对不对；
不对就把理由发回来调提示词。整个文件夹可以直接删，不影响任何东西。

**判词也会写回索引**（`index.json` 里每条的 `screen` 字段）。老条目是上一版落的，
那时还没有甄别这一步 —— `refill` / `screen` 甄别完会把判词补写回去，否则它在索引里
永远是个空白。踩过：真机跑完 `refill` 之后查"每条都有判词?"，回 `False`
（100 张里有 78 张是空白）。

### 相似度很高的图只留一张

用户的原话：「像这种相似度很高的图也只留一个」。真机上长这样：搜
"浪漫 3d 花卉 ai 图"，回来 9 张**同一个素材系列**的纸雕花卉 —— 同一位
作者、同一套底纹语言，只是裁切位置和底色不同。

`rank.py` 那层 aHash 拦不住：它把图缩到 8×8 比 64 位指纹，只能抓
"同尺寸、同裁切、轻微压缩"。**换个尺寸或裁掉一条边就翻转 10~20 位**，
阈值是 6。实测一批肉眼完全一样的图（37 对），aHash 全放行了。

`similar.py` 换一把尺子：**风格签名** = HSV 直方图 8×4×4 + 灰度 16 档 +
边缘密度，归一化后算余弦。在真实产物上量出来的分布很干净：

| 两张图的关系 | 余弦 |
|---|---|
| 同一张图（换尺寸 / 加水印 / 裁边） | **0.995 ~ 1.000** |
| 白底水彩但设计不同（仙鹤粉花 vs 粉紫牡丹） | 0.985 ~ 0.993 |
| 不同风格 | 0.40 ~ 0.90 |

所以阈值定在 **0.995**，一组里留 `tile.quality` 最高的那张。实测：

| 批次 | 去重前 | 去重后 |
|---|---|---|
| 纸雕花卉那批（用户反馈的） | 37 | **31**（那 9 张同系列并成 4 张：深灰/黑底/白底各一档） |
| 国风水彩花卉 | 100 | **78** |
| 卡通兔子 | 100 | **71** |

**为什么不更狠**：0.985 那档开始出现"同风格不同设计"（0.985~0.993 里
肉眼抽查 6 对全是不同设计）。也试过"同素材包（URL 目录段相同）时放宽
到 0.90 / 0.97"——两种都误杀：前者把"红樱桃小花 / 粉牡丹大花"（0.984）
并了，后者把"两种粉牡丹"（0.993）并了。整条路删掉，只留 0.995 一条线。
宁可漏，不误杀 —— 少给几张是遗憾，把好图删掉是事故。

想更狠可以 `--sim 0.985`（自己承担误杀）；想关掉这层 `--sim 0`。
被剔的照样进 `rejected.json`，理由写着"和 PF-xxx 几乎是同一张（相似度
0.998），只留一张"，可以事后核对。

**已知边界**：带大水印（占画面一长条）或重裁切的转载图，余弦会落到
0.99 附近，认不出来。这一档宁可放过 —— 而这也还是要人眼扫一遍缩略图。

### 这里踩过的坑（别走回去）

**同一张图会漏网进来两次**。兔子那批 100 张里有一对是同一张兔子素材图鉴的两个
副本（一家站的水印版 + 另一家的无水印版）。`md5` 对不上、`aHash` 距离也没低到
阈值 —— 加过水印/被缩放过的同图，感知哈希也会拉开。**这不是去重代码写错了，是
感知哈希的能力边界**。现在是 `similar.py` 那层接住了（见上一节），但核验阶段
仍然建议人眼扫一遍缩略图。

**判词抓不住"带大标题的素材展示卡"**。黄底 + 顶部一行 `Easter's Day Bunny
Character` 这种卡片，模型判词只写"黄底卡通兔与彩蛋散点"，pattern/match 都给
true。同一批里出现好几张（还有一张是重复下载）。**只能人眼抽查**，规则拦不住：
判词里压根没有"标题/海报/文字"这些词可拦。

**留档必须先于删除，数张数必须晚于删除**。这两条都是顺序问题，踩过：
- 留档要读原图（`_raw/` 里那批、`orig/` 里那批），先删就只剩一堆空壳，
  `rejected.json` 里 `thumb` 全是空字符串；
- "现有几张"必须在**剔完之后**数。先数后删会报"已经有 100 张了，不用补"，
  然后交出去只有 85 张 —— 报的数跟实际条数对不上，用户拿到手里才发现。

**提示词必须写明"平铺性程序已经判过了"**。第一版没说，模型就自己去找
"这图看着连不连续"，把**素底居中一朵大花**、**一张图里排着 9 个纹样的素材合集**
全判成不合格 —— 实测 100 张砍掉 69 张。可这两类恰恰是项目里早就确认过的
**合法平铺花型**（几何门槛当年也误杀过它们，那次是删掉"最外圈标准差守卫"才修好的）。
补上这句话之后，同样 100 张只砍 15 张，跟肉眼判断对得上。

**一次送几张**：本地 4B 一次调用的固定开销很大（读图 + prefill）。实测同样 15 张：
一张一调 30s+、5 张一批 15s、8 张一批 10s。所以默认一批 6 张，并发默认 1
（`--vlm-workers 2` 大约再快 1.4 倍，本地单卡再高就没收益了）。

**判词自证其罪要拦掉**。4B 不会自己保持一致，真机上见过 `why="布料实拍有褶皱光影"`
却 `pattern=true`、`why="蓝白扎染硬边漏印"` 却 `match=true` —— 用户读到判词只会觉得
机器在瞎判。`reconcile()` 做一次确定性复核：判词命中反例词（硬边/漏印/矢量/佩斯利/
曼陀罗/实拍/褶皱…）且前面没有否定词，就改判不通过，理由写成「自述「硬边漏印」，不是扎染」。
词表**故意不收"几何"**这种两面词 ——「不规则几何扎染感」是合格的花型，收了会误杀。

**还有一类更直白的**：判词已经把工艺否掉了，词表却兜不住 —— 真机漏过
`why="明显网格拼接，非扎染"`、`why="黑白噪点纹理，无扎染特征"` 两条。所以 `_denies()`
单独认「并非/不是/不属于/而非/非 + 工艺」「无/没有 + 工艺 + 特征/元素/痕迹」这两种写法。
**必须用正则、不能用"前面两个字里有否定词"**：`"无明显扎染折痕，整体晕染自然"`
是一张合格图的描述，夹了"明显"就不该算否掉 —— 早先那版按字距扫会把它误杀。

**模型输出的 JSON 靠不住**：Qwen3.5 会把多张挤进**同一个对象**里、`"i"` 键重复，
直接 `json.loads` 只会留下最后一个键。解析走"块 + 子块"两级，英文键认不出就试中文键
（实测它偶尔写 `{"图案":true,"符合需求":true}`）。这块有一整套测试钉着。

**严判的真实通过率只有 18~27%**（同一批 180 张平铺图，宽松判 90 通过、严判 27 通过）。
所以「要 100 张」实际要翻七八百个候选、还得换角度捞。翻到第 7~9 页时两家来源基本
只剩重复图，新增 268 个候选里 0 张合格 —— **这时别再翻页，换个需求说法重跑**
（`"手作扎染 蓝白晕染 布艺花型 平铺图案"` 就捞到了一批新的，一次补了 19 张）。

**别反复重判已有的那批**。同一批图连判三次，通过数 90 → 43 → 37，模型在不同批次
里的宽严会漂（同批里好图被别的图带着判）。补缺时用 `refill --no-rescreen`：
只搜新的，不动已经判过的。要重判就得接受这一批整体缩水。

**沙箱会杀进程，不是抛异常**：单轮累计删除超过 50 个文件时直接
`SAFE_DELETE_BULK_CONFIRM_REQUIRED` 退出，`try/except` 接不住。`_drop_bad`
剔 47 张要删 94 个文件，必然撞线（`_rejected` 目录 rmtree 391 个文件也一样）。
绕法：把这一进程里的 `os.remove / os.unlink / shutil.rmtree / Path.unlink`
换成 `shutil.move` 到 `/tmp`（见 `/tmp/pf_refill_driver.py`），逻辑完全等价。
**顺序上是有保障的** —— `store.append` 先写索引再清 `_raw`，半途被杀索引也是对的。


另外还有一个**尺度上宽松**的地方：左右边界都是纯白的构图（比如一张花束
海报）会被判成"能铺"——它确实能铺，只是铺出来的是"一堆花束 + 白缝"。
这类图的 `seam` 值通常贴着阈值，所以 `quality` 分会很低、排序靠后。
判定器 `tile.analyze()` 会把 `seam_h/seam_v/quality/graphic/corner_diff`
全部返回，供上层再定策略。

## 五、怎么跑

### 装环境

双击 `安装.command`，或者：

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt     # 就一个 Pillow
```

### 命令行

```bash
./.venv/bin/python run.py probe        # 环境自检：搜索源 + Pillow + 语义甄别能不能跑
./.venv/bin/python run.py keys         # 各家搜索源的地址（前六家不用申请）
./.venv/bin/python run.py search "国风 花卉 蓝白 连衣裙"  # 【路线 1】凑满 100 张
./.venv/bin/python run.py pick   "国风 花卉 水彩"        # 【路线 2】不凑数，剩多少交多少
./.venv/bin/python run.py refill "国风 花卉" --want 100   # 删掉不合格的再补满 100 张
./.venv/bin/python run.py screen --outdir out             # 只甄别，不补
./.venv/bin/python run.py tile a.jpg   # 只判几张本地图能不能平铺
./.venv/bin/python run.py one https://.../x.jpg   # 只判一张网上的图
./.venv/bin/python run.py summary      # 上次搜了多少、来自哪些站
./.venv/bin/python tools/verify.py out       # 收尾核验：产物自洽吗、判词齐吗、有残留吗
./.venv/bin/python tools/make_gallery.py --outdir out --title "国风花卉 100张"
```

**开箱即用的顺序就是 `probe` → `search`，中间不需要配任何东西。**
想要"只留合格的 100 张"，跑 `refill`（甄别默认走云端，不用先起任何服务，见第四节）。

常用参数：

```
--want 100        路线 1：要多少张**合格**的图（默认 100）；
                  路线 2：**上限**（默认 0 = 不限），不是任务
--candidates N    下载多少个候选去筛（默认 want×8；路线 2 默认 300）
--provider a,b    只用这几家（默认 = 免 key 的国内引擎 + 已配 key 的）
--page N          翻页，同一批词要更深的结果
--rounds 3        不够时最多再翻几轮页去补（路线 1 默认 3、路线 2 默认 0）
--outdir NAME     产物目录。**只写名字就自动放进 `产物/`**（`--outdir out_a`
                  → `产物/out_a`）；写绝对路径或带 `/` 的则原样用
--sim 0.995       相似去重阈值（默认 0.995，0 = 关掉这层）。0.985 更狠，
                  但会把"同风格不同设计"也并掉 —— 见第五节
--workers 12      下载并发；--per-host 4 单域名并发
--no-screen       跳过语义甄别（快很多，但实物照/展示图会混进来）
--vlm-batch 6     一次判几张；--vlm-workers 1 并发几批
--craft 扎染      点名工艺/风格（一般不用手动给，需求分析会自己抽）
--style-pos / --style-neg  自己写正反例，逗号分隔（机器判偏了时用来覆盖）
```

**看图验收**（不想翻一百个文件的时候）：

```bash
./.venv/bin/python tools/make_gallery.py --outdir 产物/out_xxx   # → _gallery.html
./.venv/bin/python tools/make_gallery.py --outdir 产物/out_xxx --side 480
```

单文件、缩略图 base64 内嵌，双击就能在浏览器里滚动看，每张下面带着机器判词。
它是辅助件（`_` 开头），不是算法产物。

### 产出在哪

**全都在 `产物/` 一个文件夹里**，一轮一个子目录（`产物/out_1017_1546/`）。
`--outdir` 只写名字就自动落到 `产物/` 下；写绝对路径则原样用。

```
产物/out_xxx/orig/          原图
产物/out_xxx/thumb/         缩略图（480 长边，和本地库一致）
产物/out_xxx/index.json     索引 —— **字段和 数据/library/index.json 对齐**
产物/out_xxx/manifest.json  这次搜索的完整记录（需求原文/用过的检索词/统计），便于复盘
产物/out_xxx/rejected.json  被剔的图 + 理由（语义甄别 + 相似去重都在这，**可以整个删**）
产物/out_xxx/_rejected/     被剔的缩略图（同上）
产物/out_xxx/_gallery.html  画廊页（make_gallery 生成，辅助件）
产物/out_xxx/_run.log       双击脚本跑时的完整日志
```

`index.json` 的字段是照本地花型库抄的（`id / name / file / w / h / md5 /
source / source_label / status / style / element / color / scene / keywords /
desc / image / full`），所以后端**不用改一行代码**就能把它当一个库来展示。
另外多写了几个全网专有的字段：

| 字段 | 为什么必须有 |
|---|---|
| `src_url` `src_page` `src_site` `src_provider` `src_query` | 图片是别人站上的，将来要追溯、要避版权全靠这几个字段 |
| `seam` `tile_quality` `graphic` | 平铺指标。这批图和普通图库最大的不同就在这，必须留在索引里 |
| `id` 用 `PF-WEB-<日期>-####` | 和库里的 `PF-LIB-` **分开** —— 全网搜回来的图还没入库，只是候选池 |
| `screen` | 语义甄别的判词（`pattern`/`match`/`why`）。留着是为了事后核对"机器凭什么判它合格" |
| `status: untagged` / `tag_mode: web` | **不假装打过标**。四维标签留空，只把检索词和标题洗出来的词放进 `keywords` |

### 当子进程用（主程序调它）

```bash
python -m wsearch.service probe   --json-out /tmp/p.json
python -m wsearch.service search  --need "国风 花卉" --outdir /tmp/out \
                                  --json-out /tmp/r.json --progress-out /tmp/prog.json
python -m wsearch.service pick    --need "国风 花卉" --outdir /tmp/out --want 0 \
                                  --json-out /tmp/r.json    # 路线 2：不凑数
python -m wsearch.service refill  --need "国风 花卉" --outdir /tmp/out --want 100 \
                                  --json-out /tmp/r.json    # 先甄别再删，再补齐
python -m wsearch.service screen  --outdir /tmp/out --json-out /tmp/r.json   # 只甄别
python -m wsearch.service one     --url https://.../x.jpg --outdir /tmp/out --json-out /tmp/r.json
python -m wsearch.service summary --outdir /tmp/out --json-out /tmp/r.json
```

契约跟随项目里另外两个算法（`atag` / `sifang` / `rhpsd`）的老规矩：

- `--json-out` 永远有 `"ok"`；失败是 `{"ok": false, "error": "人话", "stage": "..."}`；
- stdout 也打一份同样的 JSON，日志一律走 stderr；
- 退出码 `0` = 跑完了（业务失败也算，看 JSON），`2` = 参数错误；
- 进度原子写到 `--progress-out`，形状 `{phase, done, total, kept, elapsed, ts}`；
- **自检（probe）只回 ok + 一句人话，绝不回 key**；`--redact` 时连端点地址也不回
  （这条是项目里的硬规矩，因为自检结果会在后台页面上被截图）。

## 六、测试

```bash
./.venv/bin/python tools/test_tile.py       # 平铺判定：42 条（合成已知答案）
./.venv/bin/python tools/test_screen.py     # 语义甄别与补齐：129 条（视觉端点也是桩的）
./.venv/bin/python tools/test_pipeline.py   # 整条产线：134 条（桩掉网络）
./.venv/bin/python tools/test_pick.py       # 路线 2（不凑数）：25 条
```

四个测试都**不联网、不需要 key、也不需要本地视觉模型在跑**：

- `test_tile.py` 用**程序合成的已知答案**当基准（正弦干涉图和周期圆点图数学上
  严格周期，一定是平铺的；渐变、纯色、随机噪声一定不是）。第一批基准原本想用
  `数据/library/orig/` 里的真图，结果发现那批"图"其实是同一张占位图重复了几十份，
  没法用来标定 —— 所以改成了自己合成。文件末尾还专门留了两条**已知缺口**用例，
  让这个局限一直看得见。
- `test_pipeline.py` 自己造一个"假搜索源" + 桩掉下载，把整条链路
  （分析 → 搜索 → 下载 → 判定 → 排序 → 落库 → service 契约）真跑一遍，
  断言的是**真实代码路径**，只是把"外面那个世界"换成了确定的。
  里面还专门有一段（`[1b]`）拿**百度/360 的真实返回样例**当输入，钉住两件
  最容易写错的事：**百度原图必须取 `replaceUrl[0].ObjURL`**（顶层那个
  `objURL` 是加密串）、以及来源站要取来源域名而不是图床域名。
- `test_pick.py` 只盯路线 2 **和路线 1 差在哪**：一次都没翻页（记录检索要过的
  页码）、剩几张交几张、`--want` 是上限不是任务、一张都没剩下时要说清是被
  哪道闸门砍的。末尾顺带钉一条回归 —— 路线 1 没有因为共用 `_land()` 被带偏
  （它照样翻页、照样报"按你要的 N 张"）。

判定器的阈值就是照这批合成图定的，写在 `wsearch/tile.py` 顶部的常量里，
每条都注明了实测依据。
