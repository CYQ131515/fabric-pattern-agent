# 经验与教训（持续追加）

每条格式：**现象 → 原因 → 规则**

---

## L1 纯明度全局阈值做 3 色 = 必然失败

- 现象：把花型按 OKLab L 直接切黑/灰/白三档，用户反馈"完全不行"。
- 原因：灰度只保留亮度；不同颜色的花如果亮度接近，会被压到同一档并粘成一片；水彩软过渡还会在没线的地方造出假边界。
- 规则：**3 色不要走"全局明度阈值"**。要走线稿法（轮廓压黑）或专色；如果必须做灰阶，用"色彩分割 + 图着色"保证相邻块不同档。

## L2 色彩分割 + 图着色能救回"型"

- 现象：同明度的粉花/蓝花在灰度里合并；改用 OKLab 三维聚类后能分开。
- 原因：色相参与了分割；相邻块强制不同灰阶后，边界被"人为"拉开。
- 规则：做色块化时**先在 OKLab 三维空间聚类**（不是只取 L），再做**图着色**（相邻分割块不能同档）。3 档时图着色尤其关键。

## L3 vtracer `--max-colors` 会偏色

- 现象：7 色源图（含 #c94f4f/#3f7d5c）量化后变成 `#345f71/#a3576d/#d98544`，红变橙、绿变蓝。
- 原因：内置量化的色彩空间/策略不可控。
- 规则：**不要用 `--max-colors` 做生产调色板**。自己算 palette（OKLab k-means / libimagequant / 人工色卡）→ `vtracer --palette`。

## L4 自动取色在低饱和水彩上发灰

- 现象：k-means/中位数自动取 3 色，得到 `#91705d/#c6b0a3/#f2e8de` 一类米灰。
- 原因：低饱和图颜色分布集中，均值趋向"米灰"。
- 规则：自动取色只当候选；**生产专色由人工/品牌色卡决定**，或按 80 分位彩度取"鲜艳代表色"并允许提高彩度。

## L5 3 色灰阶时，线稿法比块面法更保"型"

- 现象：块面法（图着色 3 档）花形能认出但轮廓软；线稿法（Sobel 轮廓压黑）轮廓清楚、更像三色丝印。
- 原因：轮廓线是"型"的骨架。
- 规则：3 色灰阶优先线稿法（Sobel top 3–5% + 可选 dilate 1px），线太碎就提高百分位或减小 dilate。

## L6 自动缩小看图会骗人

- 现象：缩略图看着"效果不错"，2× 放大后发现细茎、花蕊全断，边缘是台阶。
- 规则：**验收必须缩略 + 2× 局部两套都看**；印花稿按目标 DPI 回渲检查。

## L7 AI 图生图很难严格只出 3 个平涂色

- 现象：提示词写 "EXACTLY three flat tones, no gradients"，nano banana / gemini-3.1 仍会输出带渐变的灰度水彩。
- 原因：图像模型倾向连续调。
- 规则：**AI 只负责"黑白灰立体基稿"**（新明暗关系、保花型），**确定性算法负责压成 3 档**。不要把"严格 3 色"交给模型。

## L8 环境坑：vtracer PyPI wheel 签名 & 无头浏览器路径

- 现象 1：`import vtracer` 报 `different Team IDs`；下载的 .so 无法 ad-hoc 修复。
- 现象 2：`Edge --headless --screenshot=out.png` 不生成文件。
- 规则：vtracer 用 **GitHub Release 的 CLI 二进制**（`codesign --force --sign -`）；截图用**绝对路径 + `--user-data-dir`**。

## L9 参数调优顺序（省时间）

1. 先定色数/路线（3 灰阶？6 灰阶？专色？）
2. 再定 palette（人工优先）
3. 再调 `--filter-speckle`（先大后小，避免碎点）
4. 最后调 `--simplify`（0.8 保细节 / 2.5 减节点）
5. 每次都记录 path 数/体积，避免"看起来差不多但其实重了一倍"

## L10 交付指标

- 唯一 fill 数 = 目标色数；
- path 数、文件体积、处理耗时写入记录；
- 3 色灰阶要单独确认细线是否保留；
- 专色要给出色值与面积占比。
